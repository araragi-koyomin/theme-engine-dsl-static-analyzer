我们在做什么

两个产出 · 同一套规则与分析能力

面向开发者 · 面向自动化 · 面向 AI

我们为"写主题"这件事做了一套能自动发现并修复错误的基础设施：规则直接从开发文档提炼，写主题文件时哪里不对立刻告诉你、还能教你怎么改——最终落地为一个命令行检查工具和一个智能编辑器插件，两者背后是同一套规则和分析能力。

① 命令行检查工具

一条命令检查一个文件或整个文件夹，列出所有问题（错在哪一行、为什么错、怎么改），输出报告并给出"通过/不通过"的结论。能嵌入自动化流程，也能给 AI 助手当工具用。

# 检查整个文件夹，生成报告 $ java -jar dsl-analyzer.jar themes/ \ --format json --output report.json # AI 助手调用：拿到问题清单自动改 $ java -jar dsl-analyzer.jar lock.xml --format json {"问题":[{"说明":"src与srcExp无法共存", "严重程度":"错误","行号":8}]} → 结论：未通过

② 智能编辑器插件

让写主题文件像写普通程序一样顺手：边写边提示错误、光标停住看说明、点一下就能修、还能在变量之间跳来跳去。装在 IntelliJ 里即可用。

// 编辑器里写错了，立刻提示 <Image src="i.png" srcExp="#pic" alpha="999"/> └─ src 与 srcExp 不能同时填 └─ alpha 应在 0–255 之间 💡 点一下修复：移除 srcExp 💡 点一下修复：把 alpha 改成 255 // 点变量名 → 跳到定义处 / 改名自动同步
命令行工具与编辑器插件共享同一套规则，规则一改两边都生效一次配置，处处可用

① STAGE 01

Markdown 文档 → 规格化 JSON

② STAGE 02

JSON → RuleRepository

M2 · 纯数据层 · 无上游依赖

JsonRuleLoader 加载所有元素 JSON + 全局变量 + 规则来源，构建 DefaultRuleRepository（Map 存储，O(1) 查询）。它是对唯一查询契约——消费方依赖接口而非实现，支持 --rule-dir 外部规则库替换与测试 Mock 注入。

装配

JsonRuleLoader .loadFromClasspath(functionLibrary) → DefaultRuleRepository elementRules : Map<String,DslElementRule> globalVars : Map<String,DslGlobalVar> ruleSources : Map<String,RuleSource> aliasMap : 别名→规范名 childrenMap : 反向推导子元素

核心查询

getElementRule("Image") // → 规则条目 getConstraints("Image") // → 声明式约束 getAllowedParents("Button") // → 合法父元素 getAllowedChildren("Group") // → 反向子元素 resolveAttrAlias("Image","w") // → "width" getRootElementNames() // → M1 文件识别
消费方：M1 · M3 · M4 · M5 · M7RuleRepository.java
③ STAGE 03a

语法分析 · M3 SyntaxChecker

编译器前端

语法分析回答"文件结构对不对"——标签有没有闭合、引号有没有配对、是不是一份合法的 XML。这是最基础的一层：连结构都不对，后面的规则检查无从谈起。JDK SAX 解析 XML → 独立 AST（带行列号）+ 嵌入 ANTLR4 表达式。

检测规则

  • SYN-SAX-001 XML 结构错误（标签未闭合 / 引号缺失 / 标签不匹配）
  • SYN-001 根元素标签错误
  • SYN-003 未知元素标签（标签名不在规格中）
  • SYN-004 未知属性名（warning）

示例

// 属性值漏了右引号 → 结构错误 <Image src="i.png />> // 标签没有闭合 → 结构错误 <Group name="bg"> <Image src="i.png"/> （缺少 </Group>） // 开闭标签不匹配 → 结构错误 <Lockscreen> ... </Wallpaper>
syntaxanalysis/SyntaxChecker.java · AstBuilder.java产出 → DslFileNode (AST)
③ STAGE 03b

语义分析 · M4 Analyzers

编译器后端 · 声明式约束

语义分析回答"是否符合规则"——必填缺失、嵌套违反、取值越界、属性冲突。AnalyzerRegistry 调度 10 个 Analyzer 对照规则库做约束判定；声明式 constraint 经 ANTLR4 文法求值，condition==true 即违反，新增规则无需写 Analyzer 代码。

检测规则（部分）

  • SEM-REQ-001 必填属性缺失
  • SEM-NEST-001 父子嵌套违反
  • SEM-SCOPE-001 不支持当前应用位置
  • SEM-ATTR-001 alpha 越界 (0–255)
  • SEM-IMG-002 src / srcExp 共存冲突
// alpha=999 越界 → SEM-ATTR-001 <Image alpha="999" src="i.png"/>

声明式约束求值

// Image.json 中声明 { "ruleId":"SEM-IMG-002", "condition": "element.attrs['src']!=null AND element.attrs['srcExp']!=null", "severity":"error", "suggestedFixes":[{"text":"移除srcExp", "type":"REMOVE_ATTR","target":"srcExp"}] } // ConstraintAnalyzer 用 // DefaultRuleDslEvaluator 求值
semanticanalysis/analyzers/*.java · ruledsl/DefaultRuleDslEvaluator.java10 Analyzers → List<Diagnostic>
④ STAGE 04

Diagnostic 合成报告 + 修复建议

M5 修复 · M7 批量报告

每条诊断携带 ruleId / severity / message / 行列位置 / suggestedFixes。FixActionGenerator 把 JSON 里的修复建议转成结构化 FixAction（纯文本操作，无 UI 依赖）；BatchInspectionRunner 汇总诊断按 --format 导出报告与退出码。

FixAction 类型

SET_VALUE scaleType = "center_crop" REMOVE_ATTR 删除 srcExp ADD_ATTR 补 src CLAMP_VALUE alpha 钳制到 0-255

报告产物 + 退出码

terminal 彩色表格，人读 json 机器读，同构 golden markdown 文档化 exit 0 无 error exit 1 存在 error exit 2 致命错误

⑥ STAGE 06

实验性：让其他编辑器也能用

同一套能力，不挑编辑器

LSP 是什么

LSP（语言服务器协议）是一种通用标准：把"检查、补全、提示"这些能力做成一个独立的后台服务，任何遵循标准的编辑器都能接上去。好处是——写一次，到处能用，不用为每个编辑器单独开发。

编辑器 后台服务 ┌──────────────┐ ┌──────────────────┐ │ 你在用的 │ ◀────▶ │ 主题检查服务 │ │ 编辑器 │ 通话 │（和插件同一套规则）│ │ VSCode/Neovim │ │ │ │ Helix 等 │ │ │ └──────────────┘ └──────────────────┘ # 只要编辑器支持 LSP，就能获得： · 写错立刻提示 · 输入时补全 · 悬浮看说明 · 规则随时更新

目前的支持情况

  • 独立后台服务：一个可独立运行的检查服务，和插件用同一套规则
  • IntelliJ（LSP 版）：通过后台服务接入，获得提示 / 补全 / 悬浮
  • VS Code：装扩展即可用，配置项写在设置里
  • 其他编辑器：Neovim、Helix、coc.nvim 等均可按标准接入
  • 规则可随时切换：不用重启，改了配置立刻生效

状态：实验性。目前提示、补全、悬浮已可用；一键修复和更多能力仍在完善中。稳定版推荐用上一页的 IntelliJ 插件。

目标：让开发者用自己顺手的编辑器，都能获得同样的检查体验后续：一键修复、更多编辑器适配
