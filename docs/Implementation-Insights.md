# 主题引擎 DSL 静态分析工具 — 实现心得与总结

## 项目回顾

本项目为主题开发者提供 DSL 静态分析能力,覆盖 Lockscreen、Wallpaper、Widget、ChargingSkin 四类界面,同时交付 CLI、IntelliJ 插件、LSP server 三种形态。从需求澄清到三形态跑通,前后经历多轮迭代,踩了不少坑,也沉淀了一些经验。

## 主要收获

**一、架构隔离是复用的地基。** 项目从一开始就坚持分析内核与 IDE 解耦:Core 层不依赖任何 IDE SDK,可独立运行;Plugin 层才叠加交互能力。这条约束短期看增加了接口设计成本(参数只能用 String、基本类型,要写 Adapter 转换),长期看回报巨大——同一套内核先后喂给 CLI、IntelliJ、VS Code、Neovim、Helix,几乎零额外成本。回头看,如果没有这条底线,三形态交付根本不可能在有限人力下完成。给我的启发是:架构决策要看三步以后,别为眼前方便牺牲复用空间。

**二、声明式规则是"零代码扩展"的关键赌注。** 规则库设计成纯 JSON 数据,新增检测逻辑只追加条件字符串,不动 Analyzer 代码。这条决策让我们和用户都不必为每条新规则发版,投入产出比极高。但它也带来一个隐性成本:规则 DSL 语法要设计得既够用又不过度,求值器要稳定。中途为支持 `element.children`、`MATCHES`、boolean literal 反复修了好几轮连锁 bug,才把边界摸清楚。结论是:声明式扩展值得做,但要把 grammar 的克制放在第一位。

**三、文档先行让协作变轻。** 项目维护着 PRD、TDD、Architecture、DSL-Rule-Spec、UX-Design、bugfix-summary 一整套文档,模块设计还按 M0-M8 拆了子文档。前期觉得写文档拖进度,后期发现无论是换人接手、AI 协作、还是自己回头排查回归,文档都在替我说话。尤其是 bugfix-summary 用症状/修复/验证三段式归档 21 个 bug,排查连锁问题时一眼能看懂传播链,这价值远超当时记录的成本。

## 工程经验

**E2E fixture 驱动比单元测试更能守住质量底线。** 用 21 个真实 fixture 配 ANSWER_KEY 做端到端对比,误报率从 5.2% 降到 4.5%。单元测试容易陷入"为测而测",E2E 却能逼你直面真实文件的复杂度——嵌套、注入、字面量边界、表达式歧义,这些在单测里很难覆盖全。我的经验是:工具类项目至少要有一套金标准 fixture,作为回归的第一道闸。

**踩坑要趁早,记录要趁热。** 变量引用三件套(跳转/查找/重命名)是最折磨人的一段:注入式语言绕过宿主引用、XmlAttributeValue 不被平台当命名元素、词法器 WS→skip 让文本粘尾随空格,每一项单看都不大,但叠加起来排查了好几天。最深的教训是:踩坑当天就记下根因和上下文,否则过两周自己都会忘为什么这么改。bugfix-summary 的存在让我少走了至少一半回头路。

**克制比堆功能更重要。** PRD 里列了 Extension、Optional 两层增量功能,实际交付只做 Core 必选集。类型推断刻意不做常量折叠和符号执行,边界划清楚后实现反而稳。这种"砍掉不算"的勇气,比"再加一个特性"更难得。

## 反思与展望

项目跑通了三形态交付和声明式规则扩展这两个核心赌注,验证了"Core-Plugin 隔离 + 数据驱动规则"的方向。遗憾是部分类型诊断归类仍有偏差,LSP 的上下文解析还停在文本启发式,没来得及 AST 化。

回头看最大的成长不在具体技术,而在三件事:一是学会用约束换复用,二是学会用文档换协作效率,三是学会用克制换稳定。这些经验比任何一行代码都更值得带走。
