# FEAT001 规则中心仓同步 — PHASE 1 需求澄清

## 1. 背景

现有规则库由内置 JSON 组成。公司 DSL 规范以 Markdown 文档为主要来源，但章节可能缺失、名称不统一，且静态约束可能出现在任意章节。需要建立中心仓，使已审批的规范更新能够转换为规则库版本并由插件在用户确认后同步。

## 2. 目标

1. 中心仓扫描整篇规范 Markdown，提取规则库更新候选，不依赖固定章节或机器可读规则块。
2. 规则库版本以完整规则包发布；首版由 IntelliJ IDEA 插件在用户确认后下载、校验、切换，并保留上一个版本用于回滚。
3. Markdown 的参数说明和功能说明能够更新规则库的 `description`，供编辑器文档展示。
4. 只有能由 DSL XML/JSON 文本本身判定的明确约束，才能成为会产生诊断的 `constraints`。

## 3. 范围与硬约束

### 3.1 静态检查边界

检查输入仅限 DSL XML/JSON 文本及已安装规则包。不得读取、验证或解释 `src` 等属性指向的本地资源；不得访问网络、读取文件大小/时长/尺寸、模拟运行时或根据路径后缀推导语义。

`src` 等资源路径属性在无明确结构约束时仅是 `string`：其格式、资源能力、资源大小、显示效果等文字均属于 `description`，不得自动生成枚举、正则或 `constraints`。

### 3.2 全文候选、窄门发布

系统必须扫描全文，不得因规则不在“约束”章节而忽略它。扫描结果仅为候选；候选只有同时满足以下条件才可自动发布为 `constraints`：

1. 能定位到明确的 DSL 标签、属性、父子关系或变量关系；
2. 违规与否可只由 DSL XML/JSON 文本判断；
3. 能生成一份应命中指定 `ruleId` 的正例和一份不得命中的反例；
4. 与当前规则包、示例及同一文档的其它证据不存在冲突。

不满足上述条件的内容必须保留为 `description` 或中心仓待确认候选，绝不可自动成为插件诊断。

### 3.3 发布与同步边界

- 第一版只接受公司中心仓已审批发布的规则包。
- 本地 Markdown 转换与本地即时应用不在本功能范围内，列为后续 P1。
- 每次发布均为完整规则包，不采用客户端逐 JSON 合并或局部覆盖。
- 用户必须明确同意后插件才切换至新规则包；切换失败不得影响当前已生效版本。

## 4. 验收标准

| ID | 可测试验收场景 |
|---|---|
| AC-01 | 约束写在功能概述、参数说明或约束章节时，中心仓均能将其作为候选提取，并保存原文位置。 |
| AC-02 | `src` 的格式、文件大小、时长、资源效果等说明只更新 `description`；生成的规则包不得因此新增值内容检查。 |
| AC-03 | 对明确的文本内结构约束（例如两个属性不能共存），发布前必须存在正例、反例及指定 `ruleId` 的实际运行结果。 |
| AC-04 | 任一候选 condition 无法被当前静态检查规则语言完整验证时，该候选不得进入已发布规则包。 |
| AC-05 | 中心仓发布版本包含完整规则库与版本元数据；IntelliJ IDEA 插件在用户确认后可下载并切换到该版本。 |
| AC-06 | 下载、校验或加载失败时，客户端继续使用旧规则包；用户可回滚至上一个已安装版本。 |
| AC-07 | 未经中心仓审批或未经用户确认的规则包不得在插件中生效。 |
| AC-08 | 源文档上传人可获得该修订的转换反馈：已发布内容、已跳过内容的原文位置/原因，以及可选的重写建议；反馈不得把跳过项伪装为已生效规则。 |

## 5. 非目标

- 校验资源文件是否存在、解析媒体元数据或检查资源格式/大小/时长。
- 执行 DSL、模拟主题效果或访问设备/ROM 运行状态。
- 允许本地 Markdown 自动转换后直接影响项目规则库。
- 让模型根据自然语言自行补充未被规范明确表达的约束。
- 首版覆盖 LSP、VS Code 或 CLI 的远端规则包同步；它们在 IDEA 编辑器方案稳定后再单独立项。

## 6. 已确认决策

| 决策 | 结论 |
|---|---|
| 规则来源 | 第一版仅中心仓已审批版本。 |
| 更新粒度 | 完整规则包下载、校验、切换和回滚。 |
| 文档扫描 | 全文扫描候选，不以章节位置作为是否提取约束的依据。 |
| 发布策略 | 广撒网找候选，窄门发布为静态检查规则。 |
| `src` 处理 | 作为普通 string；资源语义仅保留在 description。 |

## 7. 待进入 PHASE 2 定义的事项

- 规则包目录、版本、完整性校验及回滚元数据契约。
- 候选规则、原文证据、置信度与待确认状态的数据结构。
- condition 的完整语法验证接口及正反例测试包格式。
- 中心仓发布 API、插件更新通知与用户确认交互契约。
- IntelliJ LSP、VS Code 与原生编辑器文档的统一规则包加载契约。
